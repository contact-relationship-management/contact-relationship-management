# 致資安長

> 工程簡報，不是法律意見、認證或稽核。內容反映截至 2026-10-11 程式碼儲存庫所顯示的情況。本文不聲稱已獲得任何認可。

## 一段話概括安全態勢

該服務**安全失敗**，按角色和按記錄控制存取，對不應看到敏感值的角色隱藏這些值，並儲存防篡改的稽核軌跡。這些控制措施已由作者實現並測試。它們**尚未經過任何獨立方的測試**（T42），因此請把下面的每一項陳述理解為“已建置並經自測”，而不是“已驗證”。

## 已知弱點（如實說明，不隱瞞）

- **沒有獨立滲透測試或威脅建模演練**（T42）。[dtac-supporting](../../../../spec/compliance/dtac-supporting.md) 中的威脅模型只是摘要，不是結構化的威脅模型。
- **發布簽名尚未在真實發布上執行**（T49）。工作流和驗證命令已存在；在推出標籤之前它們未經測試。Actions 已按提交雜湊固定。
- **欄位加密**僅覆蓋兩列，使用本地金鑰，沒有 KMS。
- 破壞性操作前的**升級再認證**尚未建置。
- **Redis 儲存個人資料**（快取的洞察、授權鍵），必須像資料庫一樣保護：TLS、密碼、不對公網暴露。
- **破玻璃**無法撤銷，只能到期，且沒有接入告警。
- 如果 Redis 故障，**限流與鎖定**退回為各副本各自計數；除非在可信代理之後設定 `TRUSTED_PROXIES`，否則未認證呼叫者共用一個桶，因此攻擊者可以鎖定其他未認證的呼叫者。
- **策略重新載入**在快取的洞察中最多需要 30 秒才會反映。
- **空閒登出**在客戶端實現。
- **冪等鍵在 API 層是可選啟用的**（T52）：不傳送 `Idempotency-Key` 的客戶端，無法避免重試的建立請求造成重複記錄。隨附的 UI 會發送。

## 部署方必須做的事

1. 保持認證開啟；提供生產金鑰和 `CONTACT_RELATIONSHIP_MANAGEMENT_REDIS_URL`。
2. 對 `break_glass_granted` 設定告警，並及時審查授權。
3. 在資料庫之外錨定稽核鏈頭，並按計劃驗證（`GET /api/audits/verify`）。
4. 保護 PostgreSQL 和 Redis（網路、TLS、憑證、備份、靜態加密）；使用提供的任務輪換欄位金鑰。
5. 合併 Dependabot 更新；重新執行供應鏈階段；部署前驗證已簽名的發布。
6. 按維運手冊進行事件回應（[operations-runbook](../../../../spec/compliance/operations-runbook.md)）。

## 漏洞處理

報告透過 [SECURITY.md](../../../../SECURITY.md) 提交。在使用任何真實資料之前，針對預發布建置委託獨立測試（T42），並在重大變更後重新測試。

## 建議的安全行動，按順序

1. 確定範圍並委託獨立滲透測試（T42）。
2. 推出第一個發布標籤以驗證簽名和驗證流程（T49）。
3. 為破玻璃和稽核鏈驗證失敗接入告警。
4. 在所有環境中讓 Redis 使用 TLS 和憑證。
5. 由 KMS 支援的欄位金鑰以及更廣的欄位覆蓋（T41 的剩餘部分）。
