# 獨立安全測試員

> 工程簡報，不是法律意見、認證或稽核。內容反映截至 2026-10-11 程式碼儲存庫所顯示的情況。本文不聲稱已獲得任何認可。

## 為什麼需要這份文件

本專案中的每一項安全控制，都是由其作者建置並測試的（CRM-T42）。這隻能說明這些控制按作者的理解在工作，並不能說明沒有遺漏。醫院和政府買家通常要求在持有真實資料之前，由獨立的第三方進行測試；在此之前，誠實的說法只能是“按高標準建置，但未經外部檢驗”（[執行長簡報](../執行長/index.md)、[資安長簡報](../資安長/index.md)）。

本頁說明應向測試機構提供什麼，以及應期待得到什麼。

## 透過意味著什麼，不意味著什麼

一份無問題的報告只說明：一個具名的團隊，在具名的時間內，針對具名的範圍，沒有發現嚴重問題。它**不是**認證，不是認可，也不是保證。除報告所述之外，不要把系統描述為“安全”、“已認證”或“已按某標準完成滲透測試”（[治理、風險、合規簡報](../治理-風險-合規/index.md)）。

## 選擇測試方

- 獨立於作者，也獨立於任何配置過該部署的人。
- 由具名的、經驗豐富的測試人員組成，並在適用時具備您所在市場相關的資質（例如 CREST，或英國政府工作所用的 NCSC CHECK 計劃）。要詢問的是實際執行工作的個人持有哪種資質，而不只是公司。
- 在任何測試開始之前，以書面形式同意範圍、交戰規則、保密、資料處理和責任。合約由法務團隊負責商定（[法務長簡報](../法務長/index.md)）。

## 向測試人員提供什麼

1. 一個與生產環境一致的**預發布（staging）建置**：生產配置、開啟認證、TLS、真實的 Redis 和 PostgreSQL。不要測試演示用的預設配置。
2. **僅使用合成資料。** 種子任務會建置一份不含真實人員的業務資料。真實的病患或公民資料絕不能出現在測試環境中。
3. **每個角色一個帳戶**，以便從各方面測試授權。參考策略是 `config/abac-policy.reference.json`。
4. 上面連結的文件、位於 `/api-docs/openapi.json` 的 OpenAPI 文件，以及對儲存庫的讀取許可權，使測試能夠把黑盒測試與程式碼審查結合起來。
5. **已知弱點**，讓測試人員把時間花在尚未寫明的問題上：
   - 發布簽名已建置但尚未在真實發布上執行（T49）；
   - 欄位加密僅覆蓋兩列，使用本地金鑰，沒有 KMS；
   - 升級再認證（step-up）尚未建置；
   - 破玻璃無法撤銷，只能到期，且沒有接入告警；
   - 策略重新載入在快取的洞察中最多需要 30 秒才會反映；
   - 空閒登出在客戶端實現；
   - 如果 Redis 故障，限流狀態退回為各副本各自計數。
   請他們確認或反駁每一項，而不是跳過。

## 需要書面約定的交戰規則

- 具名的測試人員、日期和來源地址；您這一側有一個 24 小時的聯絡人。
- 可以嘗試什麼（例如，未經通知不得破壞測試資料儲存），以及哪些情況必須在證明存在暴露時即停止。
- 發現嚴重問題時，在最終報告之前通知誰、如何通知。
- 報告、證據和測試人員筆記如何存放和銷燬。

## 應當得到什麼

- 一份報告，包含範圍、方法、日期、測試人員姓名和資質。
- 每項發現的嚴重程度、證據、復現步驟、受影響的元件和建議的修復方案。
- 一份明確的說明：哪些內容**沒有**被測試。
- 對已修復發現的複測，包含在合約內或單獨報價。

## 報告之後

1. 在 `spec/tasks.md` 中把每項發現分流為帶有負責人和日期的任務。
2. 在使用任何真實資料之前修復嚴重和高危發現，然後請測試人員確認修復。
3. 為每項修復添加回歸測試。專案規則是：不要為了讓某項通過而削弱測試或關卡。
4. 如實記錄結果：報告日期、範圍、發現及其狀態。更新就緒度計劃（[plan](../../../../spec/plan.md)）和合規資料包（[compliance](../../../../spec/compliance/index.md)）。
5. 發生重大變更後重新測試，並按您的風險負責人設定的週期複測。一次測試是快照，不是一種狀態。

## 工作順序

1. 先解決成本低且已知的問題，避免測試人員把預算花在重新發現它們上：第一個已簽名的發布（T49）、對破玻璃和稽核驗證失敗的告警、讓 Redis 使用 TLS 和憑證。
2. 準備預發布建置、帳戶和種子資料。
3. 商定範圍、合約和交戰規則。
4. 測試；立即接收嚴重發現。
5. 修復、複測並記錄。
6. 之後才更新對外聲明，並且只寫報告所支援的內容。

## 需要您決定的事項

1. 誰來委託、誰來負責處理發現（見[風險長簡報](../風險長/index.md)）。
2. 您所在的市場要求測試人員具備哪種資質。
3. 預算和日期，應由延誤的代價決定，而不是由方便與否決定。
4. 是在上線前測試一次，還是按週期反覆測試。
