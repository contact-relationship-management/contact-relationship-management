# 최고보안책임자를 위해

> 엔지니어링 브리핑이며, 법률 자문, 인증, 감사가 아닙니다. 2026-10-11 현재 저장소가 보여 주는
> 내용을 서술합니다. 여기의 어떤 내용도 인증 취득을 주장하지 않습니다.

## 보안 태세를 한 단락으로

이 서비스는 **안전하게 실패하고**, 역할별로 그리고 레코드별로 접근을 통제하며, 민감한 값을 볼 수 없어야 하는 역할에게 숨기고,
변조가 드러나는 감사 추적을 유지합니다. 이러한 통제는 저자들이 구현하고 테스트했습니다. 독립적인 누구도 테스트하지
**않았으므로**(T42), 아래의 모든 진술을 "검증됨"이 아니라 "구축되었고 자체 테스트됨"으로 받아들이세요.

## 통제와 확인할 곳

| 영역 | 갖춰진 것 | 확인할 곳 |
|---|---|---|
| 인증 | 오프라인으로 검증하는 PASETO v4.public, 선택 사항인 Keycloak. 운영 환경은 인증이 꺼져 있으면 시작을 거부함 | [auth](../../../../spec/auth.md) |
| 권한 부여 | 속성 기반: 읽기, 쓰기, 삭제, 파괴적 작업, `mask` 의무, 레코드 수준 검사, 관리자 전용 감사, 보존, 비상 접근 검토 | [auth](../../../../spec/auth.md), 페르소나 매트릭스 테스트 |
| 데이터 노출 | 레코드, 집계, 인사이트에 대한 마스킹. 계정 상세의 유출을 발견해 수정함 (T47) | [tasks](../../../../spec/tasks.md) |
| 비상 접근 | 서면 사유, 60분 상한, 읽기 전용, 필수 제2인 검토, 감사됨, Redis를 통해 공유 | 비상 접근 작업 T44 |
| 감사 | 같은 트랜잭션의 SHA-256 해시 체인, 추가 전용 트리거, 검증 엔드포인트. 읽기도 감사됨 | [audit](../../../../spec/audit.md) |
| 남용 방어 | 속도 제한(분당 600건)과 잠금(5분 동안 10회 실패), Redis를 통해 공유. 프로브는 제외 | T43 |
| 브라우저와 전송 | 해시를 쓰는 엄격한 CSP, 프레임 거부, `nosniff`, 리퍼러 정책, 닫힌 CORS, 보안 헤더. 브라우저 JavaScript에 토큰 없음(BFF) | UI `hooks.server.ts` |
| 데이터 보호 | 두 열에 교체를 갖춘 AES-256-GCM. 로컬 키이며 KMS 없음 | T41 |
| 공급망 | `cargo audit`, `cargo deny`, `pnpm audit`, SBOM, 다이제스트로 고정한 강화된 비루트 이미지, 매주 Dependabot 업데이트, 이미지와 SBOM에 키 없이 서명하는 릴리스 워크플로 | [control-mapping](../../../../spec/compliance/control-mapping.md), [operations-runbook](../../../../spec/compliance/operations-runbook.md) |
| 오류 | 모든 오류는 하나의 RFC 9457 문제 문서이며, `401`은 허용되는 방식을 명시함 | [api-lifecycle](../../../../spec/compliance/api-lifecycle.md) |
| 메모리 안전성 | `forbid(unsafe_code)`, clippy pedantic | `src/lib.rs` |

## 알려진 약점 (숨기지 않고 밝힘)

- **독립적인 침투 테스트나 위협 모델링 작업이 없습니다** (T42).
  [dtac-supporting](../../../../spec/compliance/dtac-supporting.md)의 위협 모델은 요약이며 구조화된 것이 아닙니다.
- **릴리스 서명은 실제 릴리스에서 실행된 적이 없습니다** (T49). 워크플로와 검증 명령은 있지만, 태그가 푸시되기 전까지는
  테스트되지 않았습니다. 액션은 커밋 해시로 고정되어 있습니다.
- **필드 암호화**는 로컬 키로 두 열을 다루며 KMS는 없습니다.
- 파괴적 작업 전의 **단계적 재인증**은 구현되지 않았습니다.
- **Redis는 개인 데이터를 보관하며**(캐시된 인사이트, 부여 키) 데이터베이스처럼 보호해야 합니다. TLS, 비밀번호, 공개
  노출 금지.
- **비상 접근**은 폐기할 수 없고 만료만 되며, 연결된 경보가 없습니다.
- **속도 제한과 잠금**은 Redis가 실패하면 복제본별 집계로 되돌아갑니다. 인증되지 않은 버킷은 주소별이며,
  `TRUSTED_PROXIES`에 나열되지 않은 프록시 뒤에서는 그 주소가 프록시의 것이므로, 공격자가 인증되지 않은 다른 호출자를 잠글 수
  있습니다. 유효한 토큰을 가진 호출자는 그 주체(subject)로 집계됩니다.
- **정책 재적재**는 캐시된 인사이트에 최대 30초 뒤에 나타납니다.
- **유휴 로그아웃**은 클라이언트 측에서 이루어집니다.
- **멱등성 키**는 API에서 선택 사항입니다(T52). `Idempotency-Key`를 보내지 않는 클라이언트는 재시도한 생성이 레코드를
  중복시키는 것으로부터 보호되지 않습니다. 번들 UI는 이를 보냅니다.

## 배포자가 해야 할 일

1. 인증을 켜 두고, 운영 키와 `CONTACT_RELATIONSHIP_MANAGEMENT_REDIS_URL`을 제공하세요.
2. `break_glass_granted`에 경보를 걸고 부여를 신속히 검토하세요.
3. 감사 체인 헤드를 데이터베이스 밖에 고정하고 일정에 따라 검증하세요(`GET /api/audits/verify`).
4. PostgreSQL과 Redis를 보호하세요(네트워크, TLS, 자격 증명, 백업, 저장 시 암호화). 제공된 작업으로 필드 키를 교체하세요.
5. Dependabot 업데이트를 병합하고, 공급망 단계를 다시 실행하고, 배포 전에 서명된 릴리스를 검증하세요.
6. 사고 대응은 런북을 따르세요([operations-runbook](../../../../spec/compliance/operations-runbook.md)).

## 취약점 처리

보고는 [SECURITY.md](../../../../SECURITY.md)를 통해 합니다. 실제 데이터를 다루기 전에 스테이징 빌드를 대상으로 독립적인
테스트(T42)를 의뢰하고, 중대한 변경 후에는 다시 테스트하세요.

## 권장 보안 조치, 순서대로

1. 독립적인 침투 테스트의 범위를 정하고 의뢰하세요(T42).
2. 서명과 검증을 입증하도록 첫 릴리스 태그를 푸시하세요(T49).
3. 비상 접근과 감사 체인 검증 실패에 대한 경보를 연결하세요.
4. 모든 환경에서 Redis를 TLS와 자격 증명 뒤에 두세요.
5. KMS 기반 필드 키와 더 넓은 필드 적용 범위(T41 잔여분).

[CTO 개요](../최고기술책임자/index.md)와 [CRO 개요](../최고위험책임자/index.md)도 참고하세요.
