# 最高セキュリティ責任者向け

> 技術者向けの概要であり、法的助言、認証、監査ではありません。2026-10-11 時点でリポジトリが
> 示している内容を述べたものです。ここでは認定を主張するものは何もありません。

## セキュリティ態勢を 1 段落で

サービスは**安全側に倒れ**、ロールとレコードによってアクセスを制御し、見るべきでないロールから機微な値を隠し、
改ざんが分かる監査証跡を保持します。これらの統制は作成者によって実装およびテストされています。
**独立した第三者によるテストは一度も受けていません**(T42)。したがって、以下の記述はすべて「構築し、自己テスト
した」ものであり、「検証済み」ではないとお考えください。

## 統制と確認先

| 領域 | 実施している内容 | 確認先 |
|---|---|---|
| 認証 | オフラインで検証される PASETO v4.public、任意の Keycloak。本番では認証が無効だと起動を拒否 | [auth](../../../../spec/auth.md) |
| 認可 | 属性ベース: 読み取り、書き込み、削除、破壊的操作、`mask` の義務、レコード単位の確認、管理者専用の監査、保持、ブレークグラスのレビュー | [auth](../../../../spec/auth.md)、ペルソナ行列テスト |
| データの露出 | レコード、集計、インサイトのマスキング。アカウント詳細の漏えいを発見して修正(T47) | [tasks](../../../../spec/tasks.md) |
| 緊急アクセス | 書面による理由、60 分の上限、読み取り専用、別の人による必須のレビュー、監査、Redis で共有 | ブレークグラスのタスク T44 |
| 監査 | 同一トランザクション内の SHA-256 ハッシュチェーン、追記専用トリガー、検証エンドポイント、読み取りの監査 | [audit](../../../../spec/audit.md) |
| 不正利用への耐性 | レート制限(毎分 600)とロックアウト(5 分間に 10 回の失敗)、Redis で共有、プローブは対象外 | T43 |
| ブラウザーと通信 | ハッシュ付きの厳格な CSP、フレームの拒否、`nosniff`、リファラーポリシー、閉じた CORS、安全なヘッダー、ブラウザーの JavaScript にトークンなし(BFF) | UI の `hooks.server.ts` |

| サプライチェーン | `cargo audit`、`cargo deny`、`pnpm audit`、SBOM、ダイジェストで固定された堅牢化済みの非 root イメージ、毎週の Dependabot 更新、イメージと SBOM に鍵なしで署名するリリースワークフロー | [control-mapping](../../../../spec/compliance/control-mapping.md)、[operations-runbook](../../../../spec/compliance/operations-runbook.md) |
| エラー | すべてのエラーは 1 つの RFC 9457 問題ドキュメント。`401` は受け付ける方式を示す | [api-lifecycle](../../../../spec/compliance/api-lifecycle.md) |
| メモリ安全性 | `forbid(unsafe_code)`、clippy pedantic | `src/lib.rs` |

## 既知の弱点(隠さず、明記します)

- **独立したペネトレーションテストも脅威モデリングの演習もありません**(T42)。
  [dtac-supporting](../../../../spec/compliance/dtac-supporting.md) の脅威モデルは要約であり、
  構造化されたものではありません。
- **リリース署名は実際のリリースで実行されていません**(T49)。ワークフローと検証コマンドはありますが、
  タグをプッシュするまでテストされていません。Actions はコミットハッシュで固定されています。
- **フィールド暗号化**は 2 つの列を対象とし、ローカル鍵で、KMS はありません。
- 破壊的操作の前の**ステップアップ再認証**は構築されていません。
- **Redis は個人データを保持します**(キャッシュされたインサイト、付与キー)。データベースと同様に
  保護する必要があります: TLS、パスワード、公開しない。
- **ブレークグラス**は取り消せず、期限切れを待つしかなく、アラートも未接続です。
- **レート制限とロックアウト**は、Redis が停止するとレプリカごとのカウントに切り替わります。認証なしの
  バケットはアドレス単位で、`TRUSTED_PROXIES` に載っていないプロキシの背後ではそのプロキシのものになるため、
  攻撃者が他の認証なしの呼び出し元をロックアウトできます。有効なトークンを持つ呼び出し元は、サブジェクトで
  数えられます。
- **ポリシーの再読み込み**は、キャッシュされたインサイトに最大 30 秒後に反映されます。
- **アイドル時のサインアウト**はクライアント側です。
- **冪等性キー**は API では任意です(T52)。`Idempotency-Key` を送らないクライアントは、再試行された作成に
  よるレコードの重複から保護されません。同梱の UI は送ります。

## 導入者が行うべきこと

1. 認証を有効に保ち、本番用の鍵と `CONTACT_RELATIONSHIP_MANAGEMENT_REDIS_URL` を用意する。
2. `break_glass_granted` にアラートを設定し、付与を速やかにレビューする。
3. 監査チェーンの先頭をデータベース外に固定し、定期的に検証する
   (`GET /api/audits/verify`)。
4. PostgreSQL と Redis を保護する(ネットワーク、TLS、認証情報、バックアップ、保存時の暗号化)。提供された
   タスクでフィールド鍵をローテーションする。
5. Dependabot の更新をマージし、サプライチェーンの段階を再実行し、署名付きリリースをデプロイ前に検証する。
6. インシデント対応はランブックに従う
   ([operations-runbook](../../../../spec/compliance/operations-runbook.md))。

## 脆弱性への対応

報告は [SECURITY.md](../../../../SECURITY.md) を通じて行います。実際のデータを扱う前に、ステージングビルドに
対する独立したテスト(T42)を依頼し、大きな変更の後に再テストしてください。

## 推奨されるセキュリティ対応(順番に)

1. 独立したペネトレーションテストの範囲を決め、依頼する(T42)。
2. 最初のリリースタグをプッシュして、署名と検証を実証する(T49)。
3. ブレークグラスと、監査チェーンの検証失敗に対するアラートを接続する。
4. すべての環境で Redis を TLS と認証情報の背後に置く。
5. KMS によるフィールド鍵と、より広いフィールドの対象範囲(T41 の残り)。

[CTO 向け概要](../最高技術責任者/index.md)と [CRO 向け概要](../最高リスク責任者/index.md)も参照してください。
