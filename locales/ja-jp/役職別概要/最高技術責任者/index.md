# 最高技術責任者向け

> 技術者向けの概要であり、法的助言、認証、監査ではありません。2026-10-11 時点でリポジトリが
> 示している内容を述べたものです。ここでは認定を主張するものは何もありません。

## アーキテクチャ

- **サービス:** Axum と axa(sqlx 0.9)上の Rust、PostgreSQL 18、キャッシュ、共有カウンター、ブレークグラスの
  伝播のための Redis。`forbid(unsafe_code)`、clippy pedantic。動作の根拠となる情報源は仕様です
  ([index](../../../../spec/index.md)、[architecture](../../../../spec/architecture.md))。
- **UI:** SvelteKit 3 / Svelte 5。トークンがブラウザーの JavaScript に届くことのないバックエンド・フォー・
  フロントエンドのプロキシ、ハッシュ付きの厳格な CSP。
- **認証:** オフラインで検証される PASETO v4.public、任意の Keycloak。共有エンジンによる属性ベースの
  アクセス制御(読み取り/書き込み/削除/破壊的操作、`mask` の義務、レコード単位の確認)。
- **監査:** 変更と同じトランザクションで書き込まれる SHA-256 ハッシュチェーン、追記専用トリガー、
  `GET /api/audits/verify` で検証可能。
- **データ保護:** 2 つの列に対する、鍵ローテーション付きの AES-256-GCM フィールド暗号化。ローカル鍵で、
  KMS なし。

## 品質の証拠

ユニットテスト(185)、データベーステスト(56。強制、マスキング、監査、ページ分割、キャッシュ、冪等性、
スキーマ検査を含む)、フロントエンドのユニット(106)、Playwright(98。axe によるアクセシビリティスキャンを
含む)。CI は fmt、clippy、テスト、フロントエンドのビルドとリント、サプライチェーンの段階(`cargo audit`、
`cargo deny`、`pnpm audit`、CycloneDX SBOM)を GitHub Actions と Woodpecker で実行します。1 つのコマンドで
再現できます: `scripts/ci-check.sh`。

## 技術的負債と正直な限界

- ページ分割はオフセット方式のカーソルを使います(走査の途中でデータが変わると、行が飛んだり繰り返されたり
  することがあります)。設計上、総件数はありません。
- 冪等性キーは API では任意です(T52)。再試行によるレコードの重複から保護されるには、クライアントが作成時に
  `Idempotency-Key` を送る必要があります。同梱の UI は、すべての作成で送ります。
- OpenAPI スキーマは手書きです。リクエスト、一覧、詳細の読み取り、ダッシュボード、インサイトのビュー、
  監査、プライバシー、ブレークグラスを対象とします。状態遷移と、更新後のレコードを返すアップサートは
  型付けされていません。ルートとドキュメントが食い違うとテストが失敗し、別のテストが、マスクされたものを
  含む実際の応答をスキーマと照合します
  ([gds-api-review](../../../../spec/compliance/gds-api-review.md))。
- エラーは RFC 9457 の問題ドキュメントです(T54)。従来の `error` と `description` のメンバーは維持されます。
  ルーターの外側の層(サイズ制限、タイムアウト)で発生するエラーは変換されません。バージョン管理と廃止の
  ポリシーは [api-lifecycle](../../../../spec/compliance/api-lifecycle.md) です。`Deprecation` と `Sunset` の
  ヘッダーは仕様化されていますが、構築されていません。
- フィールド暗号化は 2 つの列を対象とし、KMS との統合はありません。
- レート制限とキャッシュの状態は、複数レプリカで正しく動作するために Redis を必要とします。
- インサイトのビューはロールごとにマスクされますが、呼び出し元のトークンごとに 30 秒間キャッシュされます。
- 破壊的操作の前のステップアップ再認証には、ID プロバイダー側の作業が必要です。

## 推奨される技術的な順序

1. KMS によるフィールド鍵と、より広いフィールドの対象範囲(T41 の残り)。
2. 最初のリリースにタグを付けて、鍵なしの署名と検証を実証し(T49)、レビュアーに API 標準の草案を
   確認してもらう。
3. 最初の廃止に合わせて `Deprecation` と `Sunset` のヘッダーを構築する。
4. ステージングビルドに対する独立したテスト(T42)を依頼する。
