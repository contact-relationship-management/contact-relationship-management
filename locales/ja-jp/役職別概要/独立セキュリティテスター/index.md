# 独立セキュリティテスター

> 技術者向けの概要であり、法的助言、認証、監査ではありません。2026-10-11 時点でリポジトリが
> 示している内容を述べたものです。ここでは認定を主張するものは何もありません。

## このページがある理由

このプロジェクトのセキュリティ統制はすべて、作成者によって構築され、テストされました(CRM-T42)。
それは、統制が作成者の理解どおりに動作することを示します。何も欠けていないことを示すものではありません。
病院や政府の購入者は、実際のデータを保持する前に、独立した第三者によるテストを求めるのが通常で、
それまでの正直な主張は「高い水準で構築されたが、外部の者による検証は受けていない」です
([CEO 向け概要](../最高経営責任者/index.md)、
[セキュリティ向け概要](../最高セキュリティ責任者/index.md))。

このページは、テスト会社に渡すべきものと、返ってくるべきものを示します。

## 合格が意味すること、意味しないこと

問題のない報告書が述べるのは、名前の挙がったチームが、示された期間と範囲で、重大な問題を見つけなかった、
ということです。それは認証でも、認定でも、保証でも**ありません**。報告書が述べる範囲を超えて、システムを
「安全」、「認証済み」、「標準に沿ってペネトレーションテスト済み」と表現してはいけません
([GRC 向け概要](../ガバナンス・リスク・コンプライアンス/index.md))。

## テスターの選び方

- 作成者から、また導入の設定を行った誰からも独立していること。
- 実名で経験豊富なテスターが担当し、該当する場合はあなたの市場に関係する認定を持っていること(たとえば
  CREST、または英国政府の業務向けの NCSC CHECK 制度)。会社だけでなく、実際に作業する個人をどの認定が
  対象としているかを尋ねてください。
- テストを始める前に、範囲、交戦規則、秘密保持、データの取り扱い、責任について書面で合意していること。
  契約は法務チームが合意するものです([CLO 向け概要](../最高法務責任者/index.md))。

## 何をテストするか

| 領域 | テスターが試すべきこと | 設計が説明されている場所 |
|---|---|---|
| 認証 | 偽造、期限切れ、リプレイ、宛先違いのトークン、認証なしへのダウングレード、認証が無効だと実行を拒否する起動時の検査 | [auth](../../../../spec/auth.md) |
| 認可 | あるロールが到達すべきでないレコードや操作への到達: 水平および垂直の権限昇格、レコード単位の確認、破壊的操作、管理者専用の読み取り(監査、保持、ブレークグラスのレビュー) | [auth](../../../../spec/auth.md) |
| データの露出 | マスクされた値が、一覧、まとめた詳細の読み取り、インサイト、集計、エラーメッセージ、キャッシュ、キャッシュキーから漏れること | [tasks](../../../../spec/tasks.md)(T32、T47) |
| 緊急アクセス | ブレークグラスの取得、延長、悪用、自分の付与のレビュー、二重のレビュー | [auth](../../../../spec/auth.md)(T44) |
| 監査 | 履歴の改変、削除、並べ替え、チェーンの迂回、読み取りの隠蔽 | [audit](../../../../spec/audit.md) |
| 不正利用への耐性 | レート制限とロックアウトの回避、他のユーザーのロックアウト、クライアントキーのためのヘッダー偽装 | T43 |
| 入力の取り扱い | インジェクション(SQL、JSON、ヘッダー)、過大な本文、不正な形式のカーソルと冪等性キー、呼び出し元をまたいだキーのリプレイや衝突 | T51、T52 |
| ウェブのフロントエンド | クロスサイトスクリプティング、リクエスト偽造、セッション処理、バックエンド・フォー・フロントエンドのプロキシ、コンテンツセキュリティポリシー、クリックジャッキング | UI の `hooks.server.ts` |
| 出荷時のインフラストラクチャ | コンテナイメージ、公開されたポート、Redis と PostgreSQL への到達性、シークレットの扱い、設定の既定値 | [operations-runbook](../../../../spec/compliance/operations-runbook.md) |
| サプライチェーン | 依存関係とイメージの出所、SBOM、署名のないビルド | [control-mapping](../../../../spec/compliance/control-mapping.md) |
| ビジネスロジック | 送信経路での同意の迂回、データが残る削除、スコアの操作、重複作成 | [regulatory](../../../../spec/regulatory.md) |

**別途合意しない限り範囲外:** トークンを発行する ID サービス(このリポジトリの外にあります)、
ホスティング基盤、大量の負荷によるサービス拒否。

## テスターに渡すもの

1. 本番で動くものに一致する**ステージングビルド**: 本番の設定、認証有効、TLS、実際の Redis と PostgreSQL。
   デモの既定値をテストしてはいけません。
2. **合成データのみ。** シードタスクは、実在の人物を含まない取引の一式を構築します。実際の患者や市民のデータを
   テスト環境に置いてはいけません。
3. **ロールごとに 1 つのアカウント。** 認可を各側からテストできるようにするためです。基準となるポリシーは
   `config/abac-policy.reference.json` です。
4. 上にリンクしたドキュメント、`/api-docs/openapi.json` の OpenAPI ドキュメント、リポジトリへの読み取り
   アクセス。テストでブラックボックスとコードレビューを組み合わせられるようにするためです。
5. **既知の弱点**。テスターが、すでに書かれていないことに時間を使えるようにするためです。
   - リリース署名は構築済みだが、実際のリリースでは未実行(T49)
   - フィールド暗号化は 2 つの列を対象とし、ローカル鍵で KMS なし
   - ステップアップ再認証は未構築
   - ブレークグラスは取り消せず、期限切れを待つしかなく、アラートも未接続
   - ポリシーの再読み込みは、キャッシュされたインサイトに最大 30 秒後に反映される
   - アイドル時のサインアウトはクライアント側
   - Redis が停止すると、レート制限の状態はレプリカごとに切り替わる

   それぞれを省略せず、確認または反証するよう依頼してください。

## 書面で合意すべき交戦規則

- テスターの氏名、日付、送信元アドレス。あなた側の 24 時間対応の連絡先。
- 試してよいこと(たとえば、通知なしにテストのデータストアを破壊しないこと)と、露出の証明の時点で止めるべき
  こと。
- 重大な発見を、最終報告の前に、誰に、どのように直ちに知らせるか。
- 報告書、証拠、テスターのメモをどのように保管し、破棄するか。

## 返ってくるべきもの

- 範囲、手法、日付、テスターの氏名、認定を記した報告書。
- 各発見について、深刻度、証拠、再現手順、影響を受けるコンポーネント、推奨される修正。
- **テストしなかった**ことの明確な記述。
- 修正された発見の再テスト。契約に含まれるか、価格が示されていること。

## 報告書の後

1. すべての発見を `spec/tasks.md` で、担当者と期日を付けたタスクとしてトリアージする。
2. 実際のデータを扱う前に重大および高の発見を修正し、テスターに修正を確認してもらう。
3. 修正ごとに回帰テストを追加する。プロジェクトの規則は、何かを通すためにテストやゲートを弱めないことです。
4. 結果を正直に記録する: 報告書の日付、範囲、発見とその状況。準備状況の計画([plan](../../../../spec/plan.md))と
   コンプライアンスパック([compliance](../../../../spec/compliance/index.md))を更新する。
5. 大きな変更の後、およびリスク責任者が定めるスケジュールで再テストする。1 回のテストは断面であって、
   状態ではありません。

## 作業の順序

1. まず、安価で既知のものを片付け、テスターが予算をそれらの再発見に使わないようにする: 最初の署名付きリリース
   (T49)、ブレークグラスと監査検証の失敗に対するアラート、TLS と認証情報の背後の Redis。
2. ステージングビルド、アカウント、シードデータを準備する。
3. 範囲、契約、交戦規則に合意する。
4. テストする。重大な発見はすぐに受け取る。
5. 修正し、再テストし、記録する。
6. その後で初めて、外部向けの主張を更新する。それも報告書が裏付ける範囲に限る。

## あなたが決めること

1. 誰が依頼し、誰が発見を所有するか([CRO 向け概要](../最高リスク責任者/index.md)を参照)。
2. あなたの市場がテスターに期待する認定はどれか。
3. 予算と日付。都合の良さではなく、遅れのコストで決めます。
4. 公開前に 1 回テストするか、定期的に行うか。
