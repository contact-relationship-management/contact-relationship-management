# 독립 보안 테스터

> 엔지니어링 브리핑이며, 법률 자문, 인증, 감사가 아닙니다. 2026-10-11 현재 저장소가 보여 주는
> 내용을 서술합니다. 여기의 어떤 내용도 인증 취득을 주장하지 않습니다.

## 이 페이지가 있는 이유

이 프로젝트의 모든 보안 통제는 저자들이 만들고 테스트했습니다(CRM-T42). 이는 통제가 저자들이 이해한 대로 작동함을
보여 줍니다. 빠진 것이 없음을 보여 주지는 않습니다. 병원과 정부 구매자는 대개 실제 데이터를 보관하기 전에 독립적인
사람의 테스트를 요구하며, 그때까지의 정직한 주장은 "높은 기준으로 만들었으나 외부인이 시험하지 않았다"입니다
([CEO 개요](../최고경영자/index.md), [보안 개요](../최고보안책임자/index.md)).

이 페이지는 테스트 업체에 넘길 것과 돌려받을 것을 담고 있습니다.

## 통과의 의미와 그렇지 않은 것

깨끗한 보고서는 지정된 팀이, 지정된 기간에, 지정된 범위에서 심각한 문제를 찾지 못했다고 말합니다. 이것은 인증도, 공인도,
보증도 **아닙니다**. 보고서가 말하는 것 이상으로 시스템을 "안전하다", "인증되었다", "표준에 따라 침투 테스트를 받았다"고
묘사하지 마세요([GRC 개요](../거버넌스-위험-규정준수/index.md)).

## 테스터 선택

- 저자와, 배포를 구성한 모든 사람으로부터 독립적일 것.
- 이름이 밝혀진 경험 많은 테스터로 구성되며, 해당하는 경우 귀하의 시장에 관련된 인증을 갖출 것(예: CREST, 또는 영국
  정부 업무를 위한 NCSC CHECK 제도). 회사만이 아니라 실제 작업하는 개인에게 어떤 인증이 적용되는지 물어보세요.
- 테스트가 시작되기 전에 범위, 교전 규칙, 기밀 유지, 데이터 취급, 책임에 대해 서면으로 합의할 것. 계약은 법무팀이 합의할
  몫입니다([CLO 개요](../최고법무책임자/index.md)).

## 무엇을 테스트하는가

| 영역 | 테스터가 시도해야 할 것 | 설계가 설명된 곳 |
|---|---|---|
| 인증 | 위조, 만료, 재생된 토큰과 대상이 잘못된 토큰, 인증 없음으로의 다운그레이드, 인증이 꺼진 채 실행을 거부하는 시작 시 검사 | [auth](../../../../spec/auth.md) |
| 권한 부여 | 역할이 접근하면 안 되는 레코드나 작업에 도달하기: 수평 및 수직 권한 상승, 레코드 수준 검사, 파괴적 작업, 관리자 전용 읽기(감사, 보존, 비상 접근 검토) | [auth](../../../../spec/auth.md) |
| 데이터 노출 | 가려진 값이 목록, 묶음 상세 읽기, 인사이트, 집계, 오류 메시지, 캐싱, 캐시 키를 통해 유출됨 | [tasks](../../../../spec/tasks.md) (T32, T47) |
| 비상 접근 | 비상 접근을 받기, 연장하기, 남용하기, 자신의 부여를 검토하기, 두 번 검토하기 | [auth](../../../../spec/auth.md) (T44) |
| 감사 | 이력을 바꾸기, 지우기, 재정렬하기, 체인을 우회하기, 읽기를 숨기기 | [audit](../../../../spec/audit.md) |
| 남용 방어 | 속도 제한과 잠금 우회, 다른 사용자 잠그기, 클라이언트 키를 위한 헤더 위조 | T43 |
| 입력 처리 | 인젝션(SQL, JSON, 헤더), 지나치게 큰 본문, 잘못된 커서와 멱등성 키, 호출자 간 키 재생 또는 충돌 | T51, T52 |
| 웹 프런트엔드 | 교차 사이트 스크립팅, 요청 위조, 세션 처리, backend-for-frontend 프록시, 콘텐츠 보안 정책, 클릭재킹 | UI `hooks.server.ts` |
| 제공되는 그대로의 인프라 | 컨테이너 이미지, 노출된 포트, Redis와 PostgreSQL 도달 가능성, 비밀 정보 처리, 구성 기본값 | [operations-runbook](../../../../spec/compliance/operations-runbook.md) |
| 공급망 | 의존성과 이미지의 출처, SBOM, 서명되지 않은 빌드 | [control-mapping](../../../../spec/compliance/control-mapping.md) |
| 비즈니스 로직 | 발송 경로에서의 동의 우회, 데이터를 남기는 삭제, 점수 조작, 중복 생성 | [regulatory](../../../../spec/regulatory.md) |

**따로 합의하지 않는 한 범위 밖:** 토큰을 발급하는 신원 서비스(이 저장소 밖에 있음), 호스팅 플랫폼, 대량의 서비스 거부.

## 테스터에게 줄 것

1. 운영 환경에서 실행될 것과 일치하는 **스테이징 빌드**: 운영 구성, 인증 켜짐, TLS, 실제 Redis와 PostgreSQL. 데모 기본값을
   테스트하지 마세요.
2. **합성 데이터만.** 시드 작업은 실제 사람이 없는 영업 장부를 만듭니다. 실제 환자나 시민의 데이터는 테스트 환경에 절대
   있어서는 안 됩니다.
3. **역할마다 계정 하나**: 각 측면에서 권한 부여를 테스트할 수 있도록. 참조 정책은
   `config/abac-policy.reference.json`입니다.
4. 위에 링크된 문서, `/api-docs/openapi.json`의 OpenAPI 문서, 저장소에 대한 읽기 권한: 테스트가 블랙박스와 코드 검토를
   결합할 수 있도록.
5. **알려진 약점**: 테스터가 이미 적혀 있지 않은 것에 시간을 쓰도록.
   - 릴리스 서명은 만들어졌지만 실제 릴리스에서 실행된 적이 없음 (T49)
   - 필드 암호화는 로컬 키로 두 열을 다루며 KMS는 없음
   - 단계적 재인증은 구현되지 않음
   - 비상 접근은 폐기할 수 없고 만료만 되며, 연결된 경보가 없음
   - 정책 재적재는 캐시된 인사이트에 최대 30초 동안 나타남
   - 유휴 로그아웃은 클라이언트 측
   - Redis가 실패하면 속도 제한 상태는 복제본별로 되돌아감

   이를 건너뛰지 말고 각각 확인하거나 반박하도록 요청하세요.

## 서면으로 합의할 교전 규칙

- 이름이 밝혀진 테스터, 날짜, 출처 주소. 귀하 측의 24시간 연락처.
- 시도해도 되는 것(예: 사전 통지 없이 테스트 데이터 저장소를 파괴하지 않기)과 노출이 입증되면 멈춰야 하는 것.
- 치명적인 발견을 최종 보고서 전에 누구에게 어떻게 즉시 알릴지.
- 보고서, 증거, 테스터의 메모를 어떻게 보관하고 파기할지.

## 돌려받아야 할 것

- 범위, 방법, 날짜, 테스터 이름, 인증이 담긴 보고서.
- 심각도, 증거, 재현 단계, 영향받는 구성 요소, 권장 수정이 있는 각 발견 사항.
- 무엇을 테스트하지 **않았는지**에 대한 명확한 진술.
- 수정된 발견 사항의 재테스트. 계약에 포함하거나 별도로 가격을 매깁니다.

## 보고서 이후

1. 모든 발견 사항을 `spec/tasks.md`에 담당자와 날짜가 있는 작업으로 분류하세요.
2. 실제 데이터를 다루기 전에 치명적 및 높음 등급 발견 사항을 수정하고, 테스터에게 수정을 확인하게 하세요.
3. 수정마다 회귀 테스트를 추가하세요. 프로젝트의 규칙은 무언가를 통과시키려고 테스트나 관문을 약화하지 않는 것입니다.
4. 결과를 정직하게 기록하세요: 보고서 날짜, 범위, 발견 사항과 그 상태. 준비 계획([plan](../../../../spec/plan.md))과
   규정 준수 묶음([compliance](../../../../spec/compliance/index.md))을 갱신하세요.
5. 중대한 변경 후에, 그리고 위험 책임자가 정한 일정에 따라 재테스트하세요. 한 번의 테스트는 상태가 아니라 스냅샷입니다.

## 작업 순서

1. 테스터가 예산을 다시 찾아내는 데 쓰지 않도록, 저렴하고 이미 아는 것부터 먼저 해결하세요: 첫 서명된 릴리스(T49), 비상
   접근과 감사 검증 실패에 대한 경보, TLS와 자격 증명 뒤의 Redis.
2. 스테이징 빌드, 계정, 시드 데이터를 준비하세요.
3. 범위, 계약, 교전 규칙에 합의하세요.
4. 테스트하고, 치명적인 발견은 즉시 받으세요.
5. 수정하고, 재테스트하고, 기록하세요.
6. 그런 다음에야 외부 주장을 갱신하세요. 보고서가 뒷받침하는 범위까지만.

## 귀하를 위한 결정

1. 누가 의뢰하고 누가 발견 사항을 소유하는지([CRO 개요](../최고위험책임자/index.md) 참고).
2. 귀하의 시장이 테스터에게 기대하는 인증.
3. 편의가 아니라 지연의 비용으로 정하는 예산과 날짜.
4. 출시 전에 한 번 테스트할지, 정기적으로 테스트할지.
