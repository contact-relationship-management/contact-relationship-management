# 独立安全测试员

> 工程简报，不是法律意见、认证或审计。内容反映截至 2026-10-11 代码仓库所显示的情况。本文不声称已获得任何认可。

## 为什么需要这份文档

本项目中的每一项安全控制，都是由其作者构建并测试的（CRM-T42）。这只能说明这些控制按作者的理解在工作，并不能说明没有遗漏。医院和政府买家通常要求在持有真实数据之前，由独立的第三方进行测试；在此之前，诚实的说法只能是“按高标准构建，但未经外部检验”（[首席执行官简报](../首席执行官/index.md)、[首席安全官简报](../首席安全官/index.md)）。

本页说明应向测试机构提供什么，以及应期待得到什么。

## 通过意味着什么，不意味着什么

一份无问题的报告只说明：一个具名的团队，在具名的时间内，针对具名的范围，没有发现严重问题。它**不是**认证，不是认可，也不是保证。除报告所述之外，不要把系统描述为“安全”、“已认证”或“已按某标准完成渗透测试”（[治理、风险、合规简报](../治理-风险-合规/index.md)）。

## 选择测试方

- 独立于作者，也独立于任何配置过该部署的人。
- 由具名的、经验丰富的测试人员组成，并在适用时具备您所在市场相关的资质（例如 CREST，或英国政府工作所用的 NCSC CHECK 计划）。要询问的是实际执行工作的个人持有哪种资质，而不只是公司。
- 在任何测试开始之前，以书面形式同意范围、交战规则、保密、数据处理和责任。合同由法务团队负责商定（[首席法务官简报](../首席法务官/index.md)）。

## 测试什么

| 领域 | 测试人员应尝试什么 | 设计说明见 |
|---|---|---|
| 认证 | 伪造、过期、重放和受众错误的令牌；降级为未认证；认证关闭时拒绝运行的启动检查 | [auth](../../../../spec/auth.md) |
| 授权 | 访问某个角色不应访问的记录或操作：水平和垂直提权、记录级检查、破坏性操作、仅限管理员的读取（审计、保留、破玻璃审查） | [auth](../../../../spec/auth.md) |
| 数据暴露 | 已脱敏的值通过列表、打包的详情读取、洞察、聚合、错误信息、缓存或缓存键泄露 | [tasks](../../../../spec/tasks.md)（T32、T47） |
| 紧急访问 | 获取、延长或滥用破玻璃；审查自己的授权；重复审查 | [auth](../../../../spec/auth.md)（T44） |
| 审计 | 修改、删除或重排历史；绕过哈希链；隐藏读取记录 | [audit](../../../../spec/audit.md) |
| 抗滥用 | 绕过限流和锁定、锁定其他用户、伪造请求头以影响客户端键 | T43 |
| 输入处理 | 注入（SQL、JSON、请求头）、超大请求体、格式错误的游标和幂等键、跨调用者重放或碰撞键 | T51、T52 |
| Web 前端 | 跨站脚本、请求伪造、会话处理、后端即前端（BFF）代理、内容安全策略、点击劫持 | UI `hooks.server.ts` |
| 按交付形态的基础设施 | 容器镜像、暴露的端口、Redis 和 PostgreSQL 的可达性、密钥处理、配置默认值 | [operations-runbook](../../../../spec/compliance/operations-runbook.md) |
| 供应链 | 依赖项和镜像的来源、SBOM、未签名的构建 | [control-mapping](../../../../spec/compliance/control-mapping.md) |
| 业务逻辑 | 发送路径中绕过同意、删除后仍残留数据、操纵评分、重复创建 | [regulatory](../../../../spec/regulatory.md) |

**除非另行约定，不在范围内：** 签发令牌的身份服务（它在本仓库之外）、托管平台，以及大流量的拒绝服务测试。

## 向测试人员提供什么

1. 一个与生产环境一致的**预发布（staging）构建**：生产配置、开启认证、TLS、真实的 Redis 和 PostgreSQL。不要测试演示用的默认配置。
2. **仅使用合成数据。** 种子任务会构建一份不含真实人员的业务数据。真实的患者或公民数据绝不能出现在测试环境中。
3. **每个角色一个账户**，以便从各方面测试授权。参考策略是 `config/abac-policy.reference.json`。
4. 上面链接的文档、位于 `/api-docs/openapi.json` 的 OpenAPI 文档，以及对仓库的读取权限，使测试能够把黑盒测试与代码审查结合起来。
5. **已知弱点**，让测试人员把时间花在尚未写明的问题上：
   - 发布签名已构建但尚未在真实发布上运行（T49）；
   - 字段加密仅覆盖两列，使用本地密钥，没有 KMS；
   - 升级再认证（step-up）尚未构建；
   - 破玻璃无法撤销，只能到期，且没有接入告警；
   - 策略重新加载在缓存的洞察中最多需要 30 秒才会反映；
   - 空闲登出在客户端实现；
   - 如果 Redis 故障，限流状态退回为各副本各自计数。
   请他们确认或反驳每一项，而不是跳过。

## 需要书面约定的交战规则

- 具名的测试人员、日期和来源地址；您这一侧有一个 24 小时的联系人。
- 可以尝试什么（例如，未经通知不得破坏测试数据存储），以及哪些情况必须在证明存在暴露时即停止。
- 发现严重问题时，在最终报告之前通知谁、如何通知。
- 报告、证据和测试人员笔记如何存放和销毁。

## 应当得到什么

- 一份报告，包含范围、方法、日期、测试人员姓名和资质。
- 每项发现的严重程度、证据、复现步骤、受影响的组件和建议的修复方案。
- 一份明确的说明：哪些内容**没有**被测试。
- 对已修复发现的复测，包含在合同内或单独报价。

## 报告之后

1. 在 `spec/tasks.md` 中把每项发现分流为带有负责人和日期的任务。
2. 在使用任何真实数据之前修复严重和高危发现，然后请测试人员确认修复。
3. 为每项修复添加回归测试。项目规则是：不要为了让某项通过而削弱测试或关卡。
4. 如实记录结果：报告日期、范围、发现及其状态。更新就绪度计划（[plan](../../../../spec/plan.md)）和合规资料包（[compliance](../../../../spec/compliance/index.md)）。
5. 发生重大变更后重新测试，并按您的风险负责人设定的周期复测。一次测试是快照，不是一种状态。

## 工作顺序

1. 先解决成本低且已知的问题，避免测试人员把预算花在重新发现它们上：第一个已签名的发布（T49）、对破玻璃和审计验证失败的告警、让 Redis 使用 TLS 和凭据。
2. 准备预发布构建、账户和种子数据。
3. 商定范围、合同和交战规则。
4. 测试；立即接收严重发现。
5. 修复、复测并记录。
6. 之后才更新对外声明，并且只写报告所支持的内容。

## 需要您决定的事项

1. 谁来委托、谁来负责处理发现（见[首席风险官简报](../首席风险官/index.md)）。
2. 您所在的市场要求测试人员具备哪种资质。
3. 预算和日期，应由延误的代价决定，而不是由方便与否决定。
4. 是在上线前测试一次，还是按周期反复测试。
