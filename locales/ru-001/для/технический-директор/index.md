# Для технического директора

> Инженерная справка, а не юридическая консультация, сертификация или аудит. В ней изложено,
> что показывает репозиторий по состоянию на 2026-10-11. Ничто здесь не утверждает наличие аккредитации.

## Архитектура

- **Сервис:** Rust на Axum и axa (sqlx 0.9), PostgreSQL 18, Redis для кэша, общих счётчиков и распространения
  экстренного доступа. `forbid(unsafe_code)`, clippy pedantic. Источник истины о поведении — спецификация
  ([index](../../../../spec/index.md), [architecture](../../../../spec/architecture.md)).
- **Интерфейс:** SvelteKit 3 / Svelte 5, прокси «бэкенд для фронтенда», чтобы ни один токен не попадал в JavaScript
  браузера, строгая CSP с хешами.
- **Аутентификация:** PASETO v4.public, проверяемый автономно, необязательный Keycloak; управление доступом на основе
  атрибутов (действия чтения/записи/удаления/разрушительные, обязательство `mask`, проверки на уровне записей) из
  общего движка.
- **Аудит:** цепочка хешей SHA-256, записываемая в той же транзакции, что и изменение, триггер только для добавления,
  проверяемая по адресу `GET /api/audits/verify`.
- **Защита данных:** шифрование полей AES-256-GCM с ротацией ключей в двух столбцах; локальные ключи, без KMS.

## Свидетельства качества

Модульные тесты (185), тесты базы данных (56, включая применение правил, скрытие, аудит, разбиение на страницы,
кэширование, идемпотентность, проверки схемы), модульные тесты интерфейса (106) и Playwright (98), включая проверки
доступности axe. CI запускает fmt, clippy, тесты, сборку и линтер интерфейса и этап цепочки поставок (`cargo audit`,
`cargo deny`, `pnpm audit`, SBOM CycloneDX) в GitHub Actions и Woodpecker. Одна команда воспроизводит всё:
`scripts/ci-check.sh`.

## Технический долг и честные ограничения

- Разбиение на страницы использует курсор-смещение (строки могут пропускаться или повторяться, если данные меняются
  во время обхода); общего подсчёта нет намеренно.
- Ключи идемпотентности в API необязательны (T52): клиент должен отправить `Idempotency-Key` при создании, чтобы быть
  защищённым от того, что повтор дублирует запись. Встроенный интерфейс отправляет его при каждом создании.
- Схемы OpenAPI написаны вручную. Они охватывают запросы, списки, подробные чтения, панели, представления аналитики,
  аудит, конфиденциальность и экстренный доступ; переходы состояний и upsert, возвращающие обновлённую запись, не
  типизированы. Тест падает, когда маршрут и документ расходятся, а другие сверяют реальные ответы, включая скрытые, со
  схемами ([gds-api-review](../../../../spec/compliance/gds-api-review.md)).
- Ошибки — документы проблем RFC 9457 (T54) с сохранёнными прежними членами `error` и `description`; ошибки слоёв вне
  маршрутизатора (ограничение размера, тайм-аут) не преобразуются. Политика версионирования и вывода из эксплуатации —
  [api-lifecycle](../../../../spec/compliance/api-lifecycle.md); заголовки `Deprecation` и `Sunset` описаны, но не
  построены.
- Шифрование полей охватывает два столбца; интеграции с KMS нет.
- Состоянию ограничения частоты и кэша нужен Redis для корректности при нескольких репликах.
- Представления аналитики скрываются по ролям, но кэшируются по токену вызывающего на 30 с.
- Повторная аутентификация с повышением уровня перед разрушительными действиями требует работы с поставщиком
  идентификации.

## Рекомендуемая техническая последовательность

1. Ключи полей на основе KMS и более широкий охват полей (остаток T41).
2. Пометить первый выпуск, чтобы подтвердить подпись без ключей и проверку (T49), и попросить рецензента проверить
   черновик стандартов API.
3. Построить заголовки `Deprecation` и `Sunset` при первом выводе из эксплуатации.
4. Заказать независимое тестирование (T42) на тестовой сборке.
