# Для директора по безопасности

> Инженерная справка, а не юридическая консультация, сертификация или аудит. В ней изложено,
> что показывает репозиторий по состоянию на 2026-10-11. Ничто здесь не утверждает наличие аккредитации.

## Состояние безопасности в одном абзаце

Сервис **безопасно отказывает**, управляет доступом по ролям и по записям, скрывает чувствительные значения от ролей,
которым их видеть не следует, и ведёт журнал аудита, обнаруживающий подделку. Эти средства контроля реализованы и
протестированы авторами. Они **не проверялись никем независимым** (T42), поэтому воспринимайте каждое утверждение ниже
как «построено и проверено самостоятельно», а не «подтверждено».

## Известные слабости (названы, не скрыты)

- **Нет независимого тестирования на проникновение и моделирования угроз** (T42). Модель угроз в
  [dtac-supporting](../../../../spec/compliance/dtac-supporting.md) — это краткое изложение, а не структурированная
  модель.
- **Подпись выпусков не запускалась на реальном выпуске** (T49). Рабочий процесс и команды проверки существуют; пока не
  отправлен тег, они не проверены. Действия закреплены по хешу коммита.
- **Шифрование полей** охватывает два столбца с локальными ключами, без KMS.
- **Повторная аутентификация с повышением уровня** перед разрушительными действиями не построена.
- **Redis хранит персональные данные** (кэшированную аналитику, ключи разрешений) и должен быть защищён как база
  данных: TLS, пароль, отсутствие публичного доступа.
- **Экстренный доступ** нельзя отозвать, он может только истечь, и оповещение не подключено.
- **Ограничение частоты и блокировка** переходят на счётчики по репликам, если Redis недоступен; неаутентифицированная
  корзина считается по адресу, а за прокси, не указанным в `TRUSTED_PROXIES`, это адрес прокси, поэтому злоумышленник
  может заблокировать других неаутентифицированных вызывающих. Вызывающий с действительным токеном учитывается по своему
  субъекту.
- **Перезагрузки политик** отражаются в кэшированной аналитике до 30 секунд.
- **Выход при бездействии** выполняется на стороне клиента.
- **Ключи идемпотентности** в API необязательны (T52): клиент, не отправляющий `Idempotency-Key`, не защищён от того,
  что повторное создание дублирует запись. Встроенный интерфейс его отправляет.

## Что должен сделать развёртывающий

1. Держать аутентификацию включённой; предоставить производственные ключи и `CONTACT_RELATIONSHIP_MANAGEMENT_REDIS_URL`.
2. Оповещать о `break_glass_granted` и оперативно проверять разрешения.
3. Закрепить голову цепочки аудита вне базы данных и проверять её (`GET /api/audits/verify`) по расписанию.
4. Защитить PostgreSQL и Redis (сеть, TLS, учётные данные, резервные копии, шифрование в состоянии покоя); менять ключи
   полей с помощью предоставленной задачи.
5. Сливать обновления Dependabot; повторно запускать этап цепочки поставок; проверять подписанный выпуск перед
   развёртыванием.
6. Следовать руководству по реагированию на инциденты
   ([operations-runbook](../../../../spec/compliance/operations-runbook.md)).

## Обработка уязвимостей

Сообщения принимаются через [SECURITY.md](../../../../SECURITY.md). Закажите независимое тестирование (T42) на тестовой
сборке до любых реальных данных и повторяйте его после существенных изменений.

## Предлагаемые действия по безопасности по порядку

1. Определить объём и заказать независимое тестирование на проникновение (T42).
2. Отправить тег первого выпуска, чтобы подтвердить подпись и проверку (T49).
3. Подключить оповещения об экстренном доступе и о сбоях проверки цепочки аудита.
4. Поместить Redis за TLS и учётные данные во всех средах.
5. Ключи полей на основе KMS и более широкий охват полей (остаток T41).

См. также справки для [технического директора](../технический-директор/index.md) и
